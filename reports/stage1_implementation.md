# Этап 1 История и надёжность Narrative Engine

Дата: 12 октября 2026 года. Локальная версия: **0.4.0**. Основание: [аудит этапа 0](stage0_audit.md) и согласованные уточнения ТЗ.

Исправлены повторная обработка сообщений, восстановление веток и памяти, сохранение спорных изменений, квадратичное накопление снимков SQLite и небезопасный переход на пустое резервное хранилище. Проверки выполнены локально. Live ST и реальные модели исключены из объёма по указанию пользователя; публикация и развёртывание не выполнялись.

## История и обработка ходов

- [history.js](../src/state/history.js) строит SHA-256 цепочку по сообщениям, автору, варианту swipe и версии канона. Смена любого предшествующего сообщения инвалидирует зависимые результаты. Generation ID и request ID сохраняются как происхождение, но не входят в ключ повторной обработки.
- [StateManager](../src/state/manager.js) хранит неизменяемые records и отдельный журнал decisions. Исходное содержание не меняется при переходах proposed, confirmed, rejected, reverted, superseded. Подтверждение новой интерпретации не переписывает предыдущую.
- Память связана с исходной записью и вариантом сообщения. Активные воспоминания, выбранные delta, решения и состояние фиксируются одним bundle. Удалённый или отклонённый вариант не попадает в активную память.
- Возврат к ранее принятому swipe использует сохранённый результат только при совпадении всей цепочки предшествующих сообщений. Изменённая середина чата пересчитывается последовательно.
- Checkpoints используют идентификатор принятой записи. Снимок чужой ветки не применяется. Сохраняются стартовая точка и последние 20 текущих checkpoints; более ранняя история остаётся в журнале.
- [Runtime](../src/runtime/runtime.js) последовательно обрабатывает изменения чата, повторяет отсутствующий POST и сохраняет pending до успешного восстановления. Запоздавшие POST и строгие перезаписи проверяют актуальность чата и текста перед побочными эффектами.
- Повторный render после загрузки чата или для старого сообщения не применяет изменения повторно и не отбрасывает последующие принятые ходы.

Формат опубликован в [history.schema.json](../schemas/history.schema.json). Это версия истории 2; schemaVersion текущего состояния пока остаётся 1. Типизированные операции мира относятся к этапу 2.

## Аудит и уверенность

POST может возвращать confidence от 0 до 1. Если поле отсутствует, используется явно установленное значение 0.5. Настройка Minimum confidence находится в существующей панели Story rhythm; значение по умолчанию 0.5.

При низкой уверенности или отрицательном аудите исходное предложение сохраняется как proposed, состояние не изменяется, ход помечается pending. В текущем deep-merge формате нельзя надёжно выделить независимые бесспорные операции, поэтому сохраняется всё предложение. Это предусмотренный ТЗ вариант «при невозможности поставить pending», а не молчаливое отбрасывание хода. После появления типизированных операций можно будет принимать независимую часть изменения.

Ошибка программной валидации сохраняется как rejected с причиной. После успешного повторного POST прежнее предложение получает отдельное решение superseded. Сама запись остаётся неизменной.

## Хранение и восстановление подключения

[Серверное хранилище](../server-plugin/lib/storage.js) использует отдельные таблицы:

| Таблица | Содержание |
| --- | --- |
| storage_fields | Последнее состояние и ссылки на активную историю, версия записи |
| turn_records | Неизменяемые изменения ходов |
| turn_decisions | Неизменяемые решения об их статусе |
| turn_memories | Воспоминания с привязкой к исходной записи |
| turn_checkpoints | Ограниченное число снимков текущей ветки |

После первой записи клиент передаёт новые записи и решения, а не весь накопленный журнал. SQLite выполняет запись транзакционно. Проверка ожидаемой версии предотвращает перезапись изменений другого клиента. Старый API state сохраняется для совместимости и ограничивает новые снимки двадцатью на чат.

Контрольный сценарий на 100 ходах: 100 records, 100 decisions, 100 memories, 0 новых state_snapshots. В зависимости от настроенного интервала сохраняется до 20 checkpoints. В аудите старого механизма те же 100 последовательных сохранений накопили 5050 копий delta.

[ServerStorageAdapter](../src/memory/serverStorage.js) хранит проверенную локальную копию и версию сервера. При недоступности сервера используется эта копия. Если копии нет, состояние не подменяется пустым: движок сообщает о недоступности хранения, обычный RP-чат продолжает работать.

Восстановление выполняется через **Reconnect storage** в диагностике или `/ne-storage-recover`. Если сервер сохранил POST, но ответ потерялся, сравнение содержимого предотвращает повторную запись. Если локальная и удалённая истории разошлись, восстановление отказывается их перезаписывать и сохраняет обе версии. Автоматического слияния конфликтующих веток в этом этапе нет.

Браузерное хранилище зеркалирует успешные операции в резервную память процесса. Такая память не заменяет долговременную localforage после закрытия браузера. Кэш спрайтов использует отдельный браузерный адаптер и не переводит серверную историю в degraded из-за неподдерживаемого ключа.

## Миграция

1. Обновить клиент и серверный плагин вместе до 0.4.0: новый клиент использует API storage с версиями записей.
2. Перед первой миграцией файловой SQLite со схемы 1 создаётся согласованная копия вида `narrative-engine.sqlite3.pre-v2-<timestamp>.bak` через VACUUM INTO. При ошибке миграция не считается успешной.
3. Исходный клиентский bundle сохраняется под ключом backup-v1. Старые воспоминания сохраняются как legacyMemories, но не выдаются за подтверждённую память текущей ветки без привязки к сообщениям.
4. Legacy delta без надёжных идентификаторов ветки пересчитываются из актуального текста при следующей обработке или Rebuild. Это может потребовать дополнительных POST-вызовов. При недоступной модели остаётся pending; резервная копия сохраняется.
5. Стартовый checkpoint карточки и импортированная базовая память сохраняются. Старые данные не удаляются из резервной копии.

При использовании старого серверного плагина новый клиент сообщает об ошибке API. Тихого отката к старому способу записи полного envelope нет.

Первые два сценария выполнены по 7 раз, SQLite использует 100 отдельных измерений. Это небольшие синтетические delta без сети и моделей. Числа не являются оценкой задержки игрового хода или качества русскоязычного retrieval.

В диагностике добавлены ограниченные выборки задержек PRE/POST/reconcile, p50/p95, сообщённые провайдером токены, число ответов без usage и количество JSON repair. Реальные задержки LLM, расход токенов и качество извлечения остаются неизмеренными.

## Границы этапа и следующий шаг

Закрыты C3–C5, C7–C8 и воспроизведённые программные причины C9; устранены изменение provenance при повторной обработке, повторное использование чужих checkpoints, пустой fallback и отсутствие восстановления пропущенного POST. Исправлен запуск тестов без неподдерживаемого флага. Live-особенности хранения swipe в конкретной версии ST по-прежнему не подтверждены.

C1–C2, строгая модель предметов и параметров C6, фильтрация знаний и актуальности C10 остаются в следующих этапах. Расширенная внутренняя жизнь NPC, кампании, embeddings и ComfyUI не входят в этот этап. Уточнения о самостоятельности NPC и нераспространении случайно раскрытых знаний добавлены в POST-инструкции; полная программная реализация этих правил ещё требуется.
