# Этап 2 — модель состояния и расширяемость

Дата: 2026-10-12. Версия: 0.5.0. Реализация и проверки локальные; live SillyTavern и реальные модели исключены из объёма по решению пользователя.

## Результат

Добавлены реестр сущностей, пользовательские типы и определения параметров как данные. Поддерживаются string, number с min/max, boolean, enum, date, gameTime (HH:mm), entityRef, object с полями и list с типом элементов. Параметры ограничиваются scope; default применяется к подходящим сущностям. Required, диапазоны, ссылки и вложенные значения проверяются при каждой транзакции.

Параметры можно добавлять, изменять, переименовывать, архивировать и удалять командой без изменения кода. Ключ, label и aliases проверяются на нормализованные совпадения. Переименование переносит значения и сохраняет старый ключ в aliases. Изменения реестра увеличивают его schemaVersion. Несовместимый тип, диапазон или scope отклоняет всю транзакцию. Используемый параметр при удалении архивируется; значения и история сохраняются.

В сущности хранятся стабильный id, type, name, aliases, campaignId, необязательный sessionId, params, relations, status, временные метки и lastChangeId. Подробности значимого изменения находятся в неизменяемом журнале по этому ID. Реестр относится к текущему сохранению; общий реестр кампании и перенос между сессиями относятся к этапу 3.

## Положение и собственность

У сущности одна каноническая position: on / in / inside / holds / wears и ID цели. Новое перемещение заменяет старое положение атомарно. holder, location и container вычисляются из position; независимо записывать их нельзя. Неизвестное положение обозначается null. При inside holder не угадывается: положение контейнера можно проследить через его собственную связь.

owner изменяется только отдельной операцией set_owner. Передача предмета другому персонажу не меняет собственника. Проверяются существование ссылок, тип персонажа для holds/wears, циклы вложенности и попытки провести физическую связь через link. Архивные сущности остаются доступными для чтения истории, но новые операции над ними запрещены.

## Контракт операций

[Операции Director](../schemas/operations.schema.json): create_entity, move, set_owner, set, adjust, link, unlink, archive_entity. Неизвестная операция или лишнее поле отклоняет транзакцию. В POST операции передаются в верхнем поле ops, рядом с прежними служебными полями результата.

[Авторские операции](../schemas/author_edit.schema.json) дополнительно разрешают define_type, define_parameter, update_parameter, rename_parameter, archive_parameter, delete_parameter. Director не может выдать себе эти полномочия ни через ops, ни через свободную перезапись registry/entities.

[Журнал](../schemas/history.schema.json) сохраняет оболочку delta для совместимости. Новые записи дополнительно содержат ops, chatFingerprint, sessionId, recordedAt, gameTime и evidence; ops совпадает с delta.ops. Решения proposed / confirmed / rejected / reverted / superseded хранятся отдельно и дописываются. Ошибка операции оставляет rejected-запись с причиной, но не меняет мир и память.

## Команды и пример

`/narrative-show-registry` показывает реестр. `/narrative-show-state` показывает состояние. `/narrative-edit-world` принимает JSON с reason и ops; это явная авторская правка, а не команда внутри обычного сообщения персонажа.

Пример создания сущностей и параметра (вставить как одну slash-команду):

```text
/narrative-edit-world {"reason":"Начальные условия","ops":[{"op":"create_entity","entity":{"id":"anna","type":"character","name":"Анна"}},{"op":"create_entity","entity":{"id":"phone","type":"item","name":"Телефон"}},{"op":"set_owner","entity":"phone","owner":"anna"},{"op":"define_parameter","definition":{"key":"energy","label":"Энергия","type":"number","scope":["character"],"default":5,"validation":{"min":0,"max":10}}}]}
```

Переименование без изменения кода:

```text
/narrative-edit-world {"reason":"Уточнение названия","ops":[{"op":"rename_parameter","key":"energy","newKey":"stamina","label":"Выносливость"}]}
```

Явная авторская коррекция положения:

```text
/narrative-edit-world {"reason":"Телефон уже у Анны","ops":[{"op":"move","entity":"phone","to":{"rel":"holds","target":"anna"}}]}
```

Перед записью создаётся backup-author-<deltaId> в выбранном хранилище. Правка привязана к последнему подтверждённому ходу: при уходе с этой ветки она отключается, при возврате восстанавливается. Правка до первого хода действует как начальное условие. Старые закэшированные продолжения после новой правки помечаются superseded и требуют повторного POST. Причина и операции сохраняются в журнале.

Если есть pending-ход, автор меняет последний подтверждённый префикс. Например, может добавить отсутствующий параметр, после чего `/narrative-rebuild-state` повторит обработку. Сам факт авторской правки не подтверждает спорный текст автоматически.

## Миграция и совместимость

Схема состояния повышена с 1 до 2; версия SQLite и журнала остаётся 2. Перед миграцией старого состояния сохраняется backup-state-v1; миграция работает с копией. Ошибка не перезаписывает исходное сохранение. Старые контрольные точки мигрируют при чтении, старые записи журнала не переписываются.

Свободные characters / objects / locations сохраняются как исторические данные. Движок не угадывает ID и пространственные связи из старых строк. Для зарегистрированной сущности новые изменения принимаются только через ops: обновление той же сущности через старые карты отклоняется, включая создание и обход в одной транзакции. Legacy-поля остальных объектов, scene, timeline, relationships, knowledge, threads и world_events пока сохраняют прежний контракт.

В ветке с авторскими операциями replay намеренно начинает с базовой точки: промежуточные checkpoints не используются, чтобы не пропустить правку между ходами. Это ограничение производительности на длинных историях с ручными правками; отдельный benchmark такого сценария не выполнялся.

## Проверки

- **71 клиентский тест**: [полный вывод](stage2/client-tests.txt).
- **31 серверный тест**: [полный вывод](stage2/server-tests.txt), включая настоящий better-sqlite3.
- G1: предмет со стола переходит в руки; старая пространственная связь исчезает.
- G2: передача A → B сохраняет owner.
- G13: старое сохранение мигрирует с резервной копией; ошибки миграции и записи сохраняют исходные данные.
- Добавление, переименование, aliases, архивирование, удаление, пользовательский тип, все типы значений и несовместимые изменения схемы.
- Атомарный отказ при цикле, неизвестной ссылке, запрещённой операции и обходе реестра.
- POST → запись → перезагрузка → replay, смена и восстановление ветки, исправление перед pending-retry.
- Те же авторские и предметные записи проходят через нормализованный SQLite-журнал.

Согласованный перенос SQLite-контрактных тестов завершён: девять исходных сценариев сохранены в серверном наборе; клиентский набор использует HTTP-моки и не требует native-зависимостей сервера.

Проверки используют синтетические ответы Director. Качество извлечения реальной моделью, поведение интерфейса живого ST и производственная эксплуатация не заявляются проверенными. Публикация и развёртывание не выполнялись.
