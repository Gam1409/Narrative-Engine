# Техническое задание: автоматизированная визуализация Narrative Engine

**Цель:** сделать визуализацию в SillyTavern автоматической для обычного
игрока. Игрок устанавливает совместимые модели для ComfyUI и указывает
LoRA в карточках персонажей; расширение само выбирает визуальные
операции, workflow, маски, контроли и обработку результатов. Все общие
настройки находятся в отдельной вкладке расширения. Продвинутый
пользователь может подключать собственные workflow и LoRA.

## 1. Принципы

1.  Автоматический режим включён по умолчанию.
2.  LLM определяет **что нужно изобразить**, но не конструирует
    произвольный граф ComfyUI.
3.  Программный движок выбирает проверенную визуальную операцию,
    проверяет совместимость и собирает workflow из шаблона.
4.  Состояние Narrative Engine --- источник истины для одежды,
    предметов, поз и локаций; изображение не меняет состояние мира.
5.  Переиспользовать подходящие изображения, не запускать генерацию
    после каждого сообщения.
6.  При недоступности ComfyUI текстовая игра продолжает работать.
7.  Не обещать идеальную геометрическую согласованность при смене
    ракурса, если известен только один 2D-фон.
8.  Перед разработкой сопоставить требования с существующим кодом, не
    создавать дублирующие модули без необходимости.

## 2. Основные пользовательские сценарии

### Первый запуск

-   Пользователь открывает отдельную вкладку **«Визуализация»** в
    настройках Narrative Engine.
-   Расширение проверяет ComfyUI, модели, нужные узлы и поддерживаемые
    операции.
-   Пользователь выбирает модель или автоматический выбор совместимой
    модели.
-   Интерфейс показывает, какие возможности готовы, а какие требуют
    зависимостей.
-   Пользователь задаёт LoRA непосредственно в карточках персонажей.
-   После первоначальной настройки игра работает без ручного выбора
    workflow.

### Во время игры

1.  Narrative Engine обновляет состояние мира.
2.  Visual Planner получает структурированные изменения: персонаж,
    одежда, эмоция, поза, объекты, локация и желаемый тип кадра.
3.  Planner определяет, нужно ли новое изображение, можно ли
    переиспользовать существующее и нужно ли предложить варианты игроку.
4.  Workflow Engine выбирает совместимый шаблон и подставляет модели,
    LoRA, референсы, маски и контролы.
5.  Задача отправляется в очередь ComfyUI.
6.  Результат проверяется и связывается с версией состояния мира.
7.  Устаревший результат не должен заменять кадр более новой сцены.
8.  При ошибке сохраняется последний валидный кадр или применяется
    поддерживаемый запасной вариант.

### Выбор игрока

Если есть несколько существенно разных визуальных решений, предложить
обычно 2--4 понятных варианта: например, общий, средний или крупный
план. Выбор не блокирует продолжение диалога по умолчанию. Должна быть
возможность оставить текущий кадр. Технические названия узлов ComfyUI в
обычном режиме не показываются.

## 3. LoRA из карточки персонажа

-   LoRA указывается в карточке персонажа через понятный UI и
    поддерживаемое поле/метаданные карточки.
-   Перед реализацией проверить фактический формат карточек и API
    используемой версии SillyTavern.
-   Не ломать стандартный формат карточки и не требовать ручного
    редактирования JSON.
-   Связывать LoRA с устойчивым ID персонажа, а не только с отображаемым
    именем.
-   Поддерживать один или несколько файлов и веса, если структура данных
    это позволяет.
-   По возможности позволить обозначить назначение: идентичность,
    одежда, стиль или другое.
-   Перед генерацией проверять наличие файла в каталогах ComfyUI и
    совместимость с выбранным checkpoint/workflow.
-   Если файл не найден, показать предупреждение; не подменять его молча
    другой LoRA.
-   Изменение LoRA должно обновлять визуальный профиль и ключ кэша без
    перезапуска, если это поддерживается API.
-   LoRA персонажа не применяется к другим персонажам без явного
    правила.

В общей вкладке визуализации показывать сводку: найденные/отсутствующие
LoRA и персонажи, требующие внимания. Основное место редактирования LoRA
--- карточка персонажа.

## 4. Отдельная вкладка «Визуализация»

### Подключение

-   Адрес ComfyUI.
-   Проверка соединения и статус.
-   Версия/API, если доступна.
-   Время последней успешной проверки.

### Автоматический режим

-   Включить/выключить визуализацию.
-   Режим: «Автоматический», «Автоматический с предложением вариантов»,
    «Экспертный».
-   Частота обновления: только значимые события / более активный режим.
-   Профиль скорости/качества.
-   Максимальное число параллельных задач.
-   Поведение при долгой генерации.
-   Лимиты кэша и хранения изображений.

### Модели и возможности

-   Выбранный checkpoint или автоматический выбор.
-   Обнаруженные модели и статус совместимости.
-   Поддержка спрайтов с альфа-каналом, inpainting, масок, позы,
    глубины, референсов и LoRA.
-   Отсутствующие узлы/модели и понятные инструкции по устранению
    проблемы.

### Диагностика

-   Очередь и статус задач.
-   Ошибки последних задач.
-   Время генерации и доля попаданий в кэш.
-   Тестовая генерация и повторная проверка зависимостей.

### Экспертные настройки

По умолчанию скрыты в раскрываемом разделе: выбор конкретного workflow,
сопоставление входов и выходов, sampler/steps/CFG/denoise,
импорт/экспорт графов, дополнительные LoRA, ручное управление масками и
контролями. Показывать только параметры, поддерживаемые выбранным
workflow.

## 5. Целевая архитектура

Названия ниже --- логические роли; перед разработкой нужно сопоставить
их с существующими модулями.

### Character Visual Profile

Объединяет базовую внешность и LoRA из карточки с текущим состоянием
мира: одеждой, аксессуарами, позой и эмоцией. Не дублирует без
необходимости существующие сущности.

### Visual Intent

Структурированный запрос: операция, затронутые сущности, что сохранить,
что изменить, тип кадра, выходной формат, приоритет и допустимая
задержка. LLM не должна использовать JSON графа ComfyUI как единственный
контракт.

### Visual Planner

Решает, нужно ли изображение, какие сущности изменились визуально, что
можно переиспользовать, какую операцию вызвать и нужны ли варианты. Не
изменяет фактическое состояние мира.

### Capability Resolver

Определяет доступность и совместимость checkpoint, LoRA, узлов, методов
прозрачности, inpainting, масок, pose/depth/edge controls и референсов.
Возможность считается доступной только после проверки зависимостей.

### Workflow Registry

Версионируемый реестр операций и реализаций. Для каждой записи хранить
назначение, требования к моделям/узлам, логические входы и выходы,
параметры, ограничения, приоритет, запасной вариант и тест.

### Workflow Compiler / Adapter

Загружает шаблон, подставляет параметры, подключает модели, LoRA, маски
и контроли только в предусмотренных шаблоном местах, проверяет
обязательные входы и создаёт запрос ComfyUI. Не строить произвольные
графы без валидации.

### Visual Job Manager

Очередь и приоритеты, отмена устаревших задач, дедупликация, ограничение
параллелизма, тайм-ауты, повторы с лимитом, восстановление после
перезапуска и проверка актуальности перед публикацией результата.

### Visual Cache

Ключ должен учитывать ID/версию персонажа или локации, профиль и LoRA с
весами, checkpoint, одежду, позу, эмоцию, аксессуары, значимые объекты,
фон/маски, камеру, workflow и его версию, seed (если применимо),
разрешение и формат. Изменение значимого параметра должно инвалидировать
старый результат.

## 6. Данные сцены

### Персонажи

-   стабильный ID;
-   базовая внешность и отличительные признаки;
-   LoRA и веса;
-   текущий комплект одежды и аксессуары;
-   поза и эмоция;
-   визуальные референсы;
-   версия профиля и ссылки на готовые спрайты.

### Одежда и предметы

Одежда, которая меняется по сюжету, должна быть представлена как
отдельное состояние/сущность. Для вещей при необходимости хранить тип,
цвет, материал, особенности, состояние, принадлежность и видимость. Для
важных предметов хранить ID, положение/ориентацию, связь с
контейнером/поверхностью, состояние и референс. Не нужно отслеживать
каждую незначительную деталь фона как сущность.

### Локация и камера

Для локации хранить связь базового фона с локацией и ракурсом. По
возможности хранить расположение важных объектов и персонажей. Камера
поддерживает тип плана, угол, цель, кадрирование, соотношение сторон и
ограничения композиции. Нужно различать простое кадрирование и настоящий
новый ракурс: последний может требовать альтернативного фона, геометрии
или отдельного workflow.

## 7. Визуальные операции

### Фоны

-   Сначала искать сохранённый фон нужной локации и ракурса.
-   Для новой локации создавать базовый фон и сохранять версию.
-   Использовать описание сцены, референсы и известные пространственные
    ограничения.
-   По возможности отделять постоянную архитектуру/мебель от
    динамических элементов.

### Изменение фона и предметов

-   Для локального изменения предпочтительно использовать маску и
    inpainting.
-   Не перегенерировать весь фон, если достаточно ограниченной области.
-   Для глобальных изменений выбирать полный workflow.
-   Связывать результат с версией состояния локации.
-   Изображение само по себе не изменяет состояние мира.

### Спрайты

-   Генерировать PNG с настоящим альфа-каналом либо использовать другой
    согласованный формат прозрачности.
-   Передавать профиль персонажа, LoRA, текущую одежду, позу, эмоцию и
    аксессуары.
-   Автоматически выбирать доступный метод прозрачности.
-   Проверять альфа-канал и базовые признаки некорректного результата.
-   Не использовать изображение с нарисованным белым/цветным фоном как
    прозрачный спрайт.

### Камера

-   Сначала переиспользовать существующий ракурс.
-   Простое кадрирование по возможности выполнять без генерации.
-   Для нового ракурса использовать совместимые контроли и референсы.
-   Если точность недостижима, предложить ближайший сохранённый ракурс
    или оставить текущий кадр.
-   Не гарантировать восстановление невидимой геометрии по одному
    2D-изображению.

### Сборка кадра

По возможности собирать фон, спрайты и динамические слои отдельно.
Порядок слоёв, масштаб и позиционирование задаются состоянием сцены и
параметрами композиции.

## 8. Автоматический выбор workflow

Workflow --- не просто JSON-файл, а реализация логической операции.
Например: - создать фон; - обновить участок фона; - создать спрайт с
прозрачностью; - изменить позу; - создать иллюстрацию; - получить
альтернативный ракурс.

Для каждой операции предусмотреть основной и запасной вариант, если это
технически возможно. Автоматически добавлять маски и контролы можно
только через проверенные адаптеры и совместимые шаблоны. Наличие узла
само по себе не гарантирует работоспособность полного workflow.

## 9. Экспертный режим

Пользователь может импортировать workflow ComfyUI, выбрать операцию,
сопоставить логические входы/выходы с узлами, указать требования к
моделям, проверить граф и сохранить его как пользовательскую реализацию.
Непроверенный граф разрешён для ручного запуска, но не выбирается
автоматически.

-   Встроенные и пользовательские графы хранятся раздельно.
-   Обновления не перезаписывают пользовательские workflow.
-   Проверяются обязательные входы, выходы и зависимости.
-   Не исполняется произвольный код из импортированного графа.
-   Должна быть возможность вернуться к встроенному варианту.

## 10. Производительность и ошибки

-   Не генерировать новое изображение после каждого сообщения
    автоматически.
-   Переиспользовать кэш и дедуплицировать одинаковые задачи.
-   Необязательные варианты имеют низкий приоритет.
-   Устаревшие задачи отменять или помечать и не публиковать.
-   Ограничивать параллелизм, тайм-ауты и число повторов.
-   При отключённом ComfyUI текстовая RPG продолжает работать.
-   При отсутствии LoRA показывать предупреждение без молчаливой
    подмены.
-   Сохранять последний валидный кадр.
-   Показывать пользователю короткую причину сбоя, подробности оставлять
    в диагностике.
-   Предварительная подготовка вероятной следующей сцены допустима, но
    не должна менять игровое состояние.

## 11. Совместимость и миграции

Перед внесением изменений: 1. Провести аудит текущих visual profiles,
sprite manifests, LoRA-конфигурации, очереди ComfyUI и workflow. 2.
Проверить формат карточек персонажей и API используемой версии
SillyTavern. 3. Сопоставить целевые модули с существующими;
переиспользовать подходящие реализации. 4. Добавлять миграции БД только
для недостающих данных. 5. Сохранить обратную совместимость кампаний без
визуальных профилей. 6. Не менять публичные контракты без необходимости.

Если стандартная карточка не имеет подходящего поля LoRA, использовать
поддерживаемые metadata/extension data и предоставить понятный UI, не
требуя ручного редактирования JSON.

## 12. Критерии приёмки

### Настройки и карточки

-   [ ] Все общие настройки находятся в отдельной вкладке
    «Визуализация».
-   [ ] Соединение с ComfyUI и доступные возможности проверяются
    реально.
-   [ ] LoRA редактируется в карточке персонажа через UI/метаданные.
-   [ ] LoRA связывается с правильным ID; отсутствие файла вызывает
    предупреждение.
-   [ ] Изменение LoRA обновляет профиль и кэш.

### Workflow

-   [ ] В автоматическом режиме граф выбирается без ручного
    вмешательства.
-   [ ] Шаблоны версионируются и проверяются.
-   [ ] Маски и контроли добавляются только совместимыми адаптерами.
-   [ ] При недоступности операции используется запасной путь или
    объясняется ограничение.
-   [ ] Непроверенный пользовательский workflow не запускается
    автоматически.

### Изображения

-   [ ] Спрайт создаётся с корректным альфа-каналом.
-   [ ] Смена одежды/LoRA не возвращает устаревший спрайт.
-   [ ] Новая локация получает сохранённый базовый фон.
-   [ ] Локальное изменение по возможности не перегенерирует всю сцену.
-   [ ] Поздний результат не заменяет более актуальный кадр.

### Игровой опыт

-   [ ] Игра продолжается при недоступности ComfyUI.
-   [ ] Выбор вариантов необязателен по умолчанию.
-   [ ] Игрок может оставить текущий кадр.
-   [ ] Обычный режим не требует знания терминов ComfyUI.
-   [ ] Экспертный режим позволяет импортировать, проверить и
    зарегистрировать свой workflow.

## 13. План реализации

**Этап 0 --- аудит:** найти текущие модули, проверить карточки
SillyTavern, составить матрицу «готово / частично / отсутствует»,
определить миграции.

**Этап 1 --- UI и LoRA:** отдельная вкладка настроек,
чтение/редактирование LoRA в карточке, проверка ComfyUI и моделей.

**Этап 2 --- автоматические операции:** Visual Intent, Capability
Resolver, Workflow Registry, шаблоны, выбор основного/запасного пути.

**Этап 3 --- спрайты:** прозрачность, связь с профилем персонажа,
очередь, кэш и проверка результатов.

**Этап 4 --- фоны:** сохранение базовых фонов, локальные изменения
объектов, связь с версией состояния локации, поддержка ракурсов.

**Этап 5 --- выбор вариантов и экспертный режим:** UI альтернатив,
импорт workflow, адаптеры, тестирование и экспорт настроек.

**Этап 6 --- сквозные испытания:** реальный SillyTavern, RP-LLM, Visual
Planner и ComfyUI; длинные сценарии; отмена и восстановление очереди;
проверка одежды, предметов, ракурсов и повторного входа в локацию.

## 14. Обязательные тестовые сценарии

1.  Персонаж с одной LoRA и правильной привязкой.
2.  Персонаж с несколькими LoRA и весами.
3.  Отсутствующий или переименованный файл LoRA.
4.  Смена одежды и проверка инвалидации кэша.
5.  Изменение эмоции без ненужной полной перегенерации.
6.  Создание и повторное использование фона локации.
7.  Локальное изменение предмета с маской/inpainting.
8.  Смена камеры с корректным запасным поведением при невозможности
    точного ракурса.
9.  Две последовательные задачи, где первая завершается позже второй.
10. Отключение ComfyUI во время игры.
11. Отклонение некорректного пользовательского workflow.
12. Возврат в локацию после изменения её состояния.
13. Обновление расширения без потери пользовательских workflow и
    карточек.
14. Длинная сессия: рост очереди, кэша и БД.

## 15. Ожидаемый результат

Обычный пользователь подключает ComfyUI, устанавливает совместимые
модели и указывает LoRA непосредственно в карточках персонажей.
Narrative Engine автоматически определяет нужные визуальные изменения,
выбирает проверенные workflow, подключает поддерживаемые маски и
контроли, использует кэш и при необходимости предлагает понятные
варианты. Продвинутый пользователь может подключать дополнительные LoRA
и регистрировать собственные workflow через адаптеры.

**Главный критерий качества:** для игры в визуальную RPG пользователю не
нужно изучать внутреннее устройство ComfyUI.
