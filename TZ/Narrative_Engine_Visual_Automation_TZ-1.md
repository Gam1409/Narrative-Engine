# Техническое задание: автоматизированная визуализация Narrative Engine

**Цель:** сделать визуализацию в SillyTavern автоматической для обычного
игрока. Игрок устанавливает совместимые модели для ComfyUI и указывает
LoRA в карточках персонажей; расширение само выбирает визуальные
операции, workflow, маски, контроли и обработку результатов. Все общие
настройки находятся в отдельной вкладке расширения. Продвинутый
пользователь может подключать собственные workflow и LoRA.

## 1. Принципы

1.  Автоматический режим включён по умолчанию.
2.  LLM определяет **что нужно изобразить**, но не конструирует
    произвольный граф ComfyUI.
3.  Программный движок выбирает проверенную визуальную операцию,
    проверяет совместимость и собирает workflow из шаблона.
4.  Состояние Narrative Engine --- источник истины для одежды,
    предметов, поз и локаций; изображение не меняет состояние мира.
5.  Переиспользовать подходящие изображения, не запускать генерацию
    после каждого сообщения.
6.  При недоступности ComfyUI текстовая игра продолжает работать.
7.  Не обещать идеальную геометрическую согласованность при смене
    ракурса, если известен только один 2D-фон.
8.  Перед разработкой сопоставить требования с существующим кодом, не
    создавать дублирующие модули без необходимости.

## 2. Основные пользовательские сценарии

### Первый запуск

-   Пользователь открывает отдельную вкладку **«Визуализация»** в
    настройках Narrative Engine.
-   Расширение проверяет ComfyUI, модели, нужные узлы и поддерживаемые
    операции.
-   Пользователь выбирает модель или автоматический выбор совместимой
    модели.
-   Интерфейс показывает, какие возможности готовы, а какие требуют
    зависимостей.
-   Пользователь задаёт LoRA непосредственно в карточках персонажей.
-   После первоначальной настройки игра работает без ручного выбора
    workflow.

### Во время игры

1.  Narrative Engine обновляет состояние мира.
2.  Visual Planner получает структурированные изменения: персонаж,
    одежда, эмоция, поза, объекты, локация и желаемый тип кадра.
3.  Planner определяет, нужно ли новое изображение, можно ли
    переиспользовать существующее и нужно ли предложить варианты игроку.
4.  Workflow Engine выбирает совместимый шаблон и подставляет модели,
    LoRA, референсы, маски и контролы.
5.  Задача отправляется в очередь ComfyUI.
6.  Результат проверяется и связывается с версией состояния мира.
7.  Устаревший результат не должен заменять кадр более новой сцены.
8.  При ошибке сохраняется последний валидный кадр или применяется
    поддерживаемый запасной вариант.

### Выбор игрока

Если есть несколько существенно разных визуальных решений, предложить
обычно 2--4 понятных варианта: например, общий, средний или крупный
план. Выбор не блокирует продолжение диалога по умолчанию. Должна быть
возможность оставить текущий кадр. Технические названия узлов ComfyUI в
обычном режиме не показываются.

## 3. LoRA из карточки персонажа

-   LoRA указывается в карточке персонажа через понятный UI и
    поддерживаемое поле/метаданные карточки.
-   Перед реализацией проверить фактический формат карточек и API
    используемой версии SillyTavern.
-   Не ломать стандартный формат карточки и не требовать ручного
    редактирования JSON.
-   Связывать LoRA с устойчивым ID персонажа, а не только с отображаемым
    именем.
-   Поддерживать один или несколько файлов и веса, если структура данных
    это позволяет.
-   По возможности позволить обозначить назначение: идентичность,
    одежда, стиль или другое.
-   Перед генерацией проверять наличие файла в каталогах ComfyUI и
    совместимость с выбранным checkpoint/workflow.
-   Если файл не найден, показать предупреждение; не подменять его молча
    другой LoRA.
-   Изменение LoRA должно обновлять визуальный профиль и ключ кэша без
    перезапуска, если это поддерживается API.
-   LoRA персонажа не применяется к другим персонажам без явного
    правила.

В общей вкладке визуализации показывать сводку: найденные/отсутствующие
LoRA и персонажи, требующие внимания. Основное место редактирования LoRA
--- карточка персонажа.

## 4. Отдельная вкладка «Визуализация»

### Подключение

-   Адрес ComfyUI.
-   Проверка соединения и статус.
-   Версия/API, если доступна.
-   Время последней успешной проверки.

### Автоматический режим

-   Включить/выключить визуализацию.
-   Режим: «Автоматический», «Автоматический с предложением вариантов»,
    «Экспертный».
-   Частота обновления: только значимые события / более активный режим.
-   Профиль скорости/качества.
-   Максимальное число параллельных задач.
-   Поведение при долгой генерации.
-   Лимиты кэша и хранения изображений.

### Модели и возможности

-   Выбранный checkpoint или автоматический выбор.
-   Обнаруженные модели и статус совместимости.
-   Поддержка спрайтов с альфа-каналом, inpainting, масок, позы,
    глубины, референсов и LoRA.
-   Отсутствующие узлы/модели и понятные инструкции по устранению
    проблемы.

### Диагностика

-   Очередь и статус задач.
-   Ошибки последних задач.
-   Время генерации и доля попаданий в кэш.
-   Тестовая генерация и повторная проверка зависимостей.

### Экспертные настройки

По умолчанию скрыты в раскрываемом разделе: выбор конкретного workflow,
сопоставление входов и выходов, sampler/steps/CFG/denoise,
импорт/экспорт графов, дополнительные LoRA, ручное управление масками и
контролями. Показывать только параметры, поддерживаемые выбранным
workflow.

## 5. Целевая архитектура

Названия ниже --- логические роли; перед разработкой нужно сопоставить
их с существующими модулями.

### Character Visual Profile

Объединяет базовую внешность и LoRA из карточки с текущим состоянием
мира: одеждой, аксессуарами, позой и эмоцией. Не дублирует без
необходимости существующие сущности.

### Visual Intent

Структурированный запрос: операция, затронутые сущности, что сохранить,
что изменить, тип кадра, выходной формат, приоритет и допустимая
задержка. LLM не должна использовать JSON графа ComfyUI как единственный
контракт.

### Visual Planner

Решает, нужно ли изображение, какие сущности изменились визуально, что
можно переиспользовать, какую операцию вызвать и нужны ли варианты. Не
изменяет фактическое состояние мира.

### Capability Resolver

Определяет доступность и совместимость checkpoint, LoRA, узлов, методов
прозрачности, inpainting, масок, pose/depth/edge controls и референсов.
Возможность считается доступной только после проверки зависимостей.

### Workflow Registry

Версионируемый реестр операций и реализаций. Для каждой записи хранить
назначение, требования к моделям/узлам, логические входы и выходы,
параметры, ограничения, приоритет, запасной вариант и тест.

### Workflow Compiler / Adapter

Загружает шаблон, подставляет параметры, подключает модели, LoRA, маски
и контроли только в предусмотренных шаблоном местах, проверяет
обязательные входы и создаёт запрос ComfyUI. Не строить произвольные
графы без валидации.

### Visual Job Manager

Очередь и приоритеты, отмена устаревших задач, дедупликация, ограничение
параллелизма, тайм-ауты, повторы с лимитом, восстановление после
перезапуска и проверка актуальности перед публикацией результата.

### Visual Cache

Ключ должен учитывать ID/версию персонажа или локации, профиль и LoRA с
весами, checkpoint, одежду, позу, эмоцию, аксессуары, значимые объекты,
фон/маски, камеру, workflow и его версию, seed (если применимо),
разрешение и формат. Изменение значимого параметра должно инвалидировать
старый результат.

## 6. Данные сцены

### Персонажи

-   стабильный ID;
-   базовая внешность и отличительные признаки;
-   LoRA и веса;
-   текущий комплект одежды и аксессуары;
-   поза и эмоция;
-   визуальные референсы;
-   версия профиля и ссылки на готовые спрайты.

### Одежда и предметы

Одежда, которая меняется по сюжету, должна быть представлена как
отдельное состояние/сущность. Для вещей при необходимости хранить тип,
цвет, материал, особенности, состояние, принадлежность и видимость. Для
важных предметов хранить ID, положение/ориентацию, связь с
контейнером/поверхностью, состояние и референс. Не нужно отслеживать
каждую незначительную деталь фона как сущность.

### Локация и камера

Для локации хранить связь базового фона с локацией и ракурсом. По
возможности хранить расположение важных объектов и персонажей. Камера
поддерживает тип плана, угол, цель, кадрирование, соотношение сторон и
ограничения композиции. Нужно различать простое кадрирование и настоящий
новый ракурс: последний может требовать альтернативного фона, геометрии
или отдельного workflow.

## 7. Визуальные операции

### Фоны

-   Сначала искать сохранённый фон нужной локации и ракурса.
-   Для новой локации создавать базовый фон и сохранять версию.
-   Использовать описание сцены, референсы и известные пространственные
    ограничения.
-   По возможности отделять постоянную архитектуру/мебель от
    динамических элементов.

### Изменение фона и предметов

-   Для локального изменения предпочтительно использовать маску и
    inpainting.
-   Не перегенерировать весь фон, если достаточно ограниченной области.
-   Для глобальных изменений выбирать полный workflow.
-   Связывать результат с версией состояния локации.
-   Изображение само по себе не изменяет состояние мира.

### Спрайты

-   Генерировать PNG с настоящим альфа-каналом либо использовать другой
    согласованный формат прозрачности.
-   Передавать профиль персонажа, LoRA, текущую одежду, позу, эмоцию и
    аксессуары.
-   Автоматически выбирать доступный метод прозрачности.
-   Проверять альфа-канал и базовые признаки некорректного результата.
-   Не использовать изображение с нарисованным белым/цветным фоном как
    прозрачный спрайт.

### Камера

-   Сначала переиспользовать существующий ракурс.
-   Простое кадрирование по возможности выполнять без генерации.
-   Для нового ракурса использовать совместимые контроли и референсы.
-   Если точность недостижима, предложить ближайший сохранённый ракурс
    или оставить текущий кадр.
-   Не гарантировать восстановление невидимой геометрии по одному
    2D-изображению.

### Сборка кадра

По возможности собирать фон, спрайты и динамические слои отдельно.
Порядок слоёв, масштаб и позиционирование задаются состоянием сцены и
параметрами композиции.

## 8. Автоматический выбор workflow

Workflow --- не просто JSON-файл, а реализация логической операции.
Например: - создать фон; - обновить участок фона; - создать спрайт с
прозрачностью; - изменить позу; - создать иллюстрацию; - получить
альтернативный ракурс.

Для каждой операции предусмотреть основной и запасной вариант, если это
технически возможно. Автоматически добавлять маски и контролы можно
только через проверенные адаптеры и совместимые шаблоны. Наличие узла
само по себе не гарантирует работоспособность полного workflow.

## 9. Экспертный режим

Пользователь может импортировать workflow ComfyUI, выбрать операцию,
сопоставить логические входы/выходы с узлами, указать требования к
моделям, проверить граф и сохранить его как пользовательскую реализацию.
Непроверенный граф разрешён для ручного запуска, но не выбирается
автоматически.

-   Встроенные и пользовательские графы хранятся раздельно.
-   Обновления не перезаписывают пользовательские workflow.
-   Проверяются обязательные входы, выходы и зависимости.
-   Не исполняется произвольный код из импортированного графа.
-   Должна быть возможность вернуться к встроенному варианту.

## 10. Производительность и ошибки

-   Не генерировать новое изображение после каждого сообщения
    автоматически.
-   Переиспользовать кэш и дедуплицировать одинаковые задачи.
-   Необязательные варианты имеют низкий приоритет.
-   Устаревшие задачи отменять или помечать и не публиковать.
-   Ограничивать параллелизм, тайм-ауты и число повторов.
-   При отключённом ComfyUI текстовая RPG продолжает работать.
-   При отсутствии LoRA показывать предупреждение без молчаливой
    подмены.
-   Сохранять последний валидный кадр.
-   Показывать пользователю короткую причину сбоя, подробности оставлять
    в диагностике.
-   Предварительная подготовка вероятной следующей сцены допустима, но
    не должна менять игровое состояние.

## 11. Совместимость и миграции

Перед внесением изменений: 1. Провести аудит текущих visual profiles,
sprite manifests, LoRA-конфигурации, очереди ComfyUI и workflow. 2.
Проверить формат карточек персонажей и API используемой версии
SillyTavern. 3. Сопоставить целевые модули с существующими;
переиспользовать подходящие реализации. 4. Добавлять миграции БД только
для недостающих данных. 5. Сохранить обратную совместимость кампаний без
визуальных профилей. 6. Не менять публичные контракты без необходимости.

Если стандартная карточка не имеет подходящего поля LoRA, использовать
поддерживаемые metadata/extension data и предоставить понятный UI, не
требуя ручного редактирования JSON.

## 12. Критерии приёмки

### Настройки и карточки

-   [ ] Все общие настройки находятся в отдельной вкладке
    «Визуализация».
-   [ ] Соединение с ComfyUI и доступные возможности проверяются
    реально.
-   [ ] LoRA редактируется в карточке персонажа через UI/метаданные.
-   [ ] LoRA связывается с правильным ID; отсутствие файла вызывает
    предупреждение.
-   [ ] Изменение LoRA обновляет профиль и кэш.

### Workflow

-   [ ] В автоматическом режиме граф выбирается без ручного
    вмешательства.
-   [ ] Шаблоны версионируются и проверяются.
-   [ ] Маски и контроли добавляются только совместимыми адаптерами.
-   [ ] При недоступности операции используется запасной путь или
    объясняется ограничение.
-   [ ] Непроверенный пользовательский workflow не запускается
    автоматически.

### Изображения

-   [ ] Спрайт создаётся с корректным альфа-каналом.
-   [ ] Смена одежды/LoRA не возвращает устаревший спрайт.
-   [ ] Новая локация получает сохранённый базовый фон.
-   [ ] Локальное изменение по возможности не перегенерирует всю сцену.
-   [ ] Поздний результат не заменяет более актуальный кадр.

### Игровой опыт

-   [ ] Игра продолжается при недоступности ComfyUI.
-   [ ] Выбор вариантов необязателен по умолчанию.
-   [ ] Игрок может оставить текущий кадр.
-   [ ] Обычный режим не требует знания терминов ComfyUI.
-   [ ] Экспертный режим позволяет импортировать, проверить и
    зарегистрировать свой workflow.

## 13. План реализации

**Этап 0 --- аудит:** найти текущие модули, проверить карточки
SillyTavern, составить матрицу «готово / частично / отсутствует»,
определить миграции.

**Этап 1 --- UI и LoRA:** отдельная вкладка настроек,
чтение/редактирование LoRA в карточке, проверка ComfyUI и моделей.

**Этап 2 --- автоматические операции:** Visual Intent, Capability
Resolver, Workflow Registry, шаблоны, выбор основного/запасного пути.

**Этап 3 --- спрайты:** прозрачность, связь с профилем персонажа,
очередь, кэш и проверка результатов.

**Этап 4 --- фоны:** сохранение базовых фонов, локальные изменения
объектов, связь с версией состояния локации, поддержка ракурсов.

**Этап 5 --- выбор вариантов и экспертный режим:** UI альтернатив,
импорт workflow, адаптеры, тестирование и экспорт настроек.

**Этап 6 --- сквозные испытания:** реальный SillyTavern, RP-LLM, Visual
Planner и ComfyUI; длинные сценарии; отмена и восстановление очереди;
проверка одежды, предметов, ракурсов и повторного входа в локацию.

## 14. Обязательные тестовые сценарии

1.  Персонаж с одной LoRA и правильной привязкой.
2.  Персонаж с несколькими LoRA и весами.
3.  Отсутствующий или переименованный файл LoRA.
4.  Смена одежды и проверка инвалидации кэша.
5.  Изменение эмоции без ненужной полной перегенерации.
6.  Создание и повторное использование фона локации.
7.  Локальное изменение предмета с маской/inpainting.
8.  Смена камеры с корректным запасным поведением при невозможности
    точного ракурса.
9.  Две последовательные задачи, где первая завершается позже второй.
10. Отключение ComfyUI во время игры.
11. Отклонение некорректного пользовательского workflow.
12. Возврат в локацию после изменения её состояния.
13. Обновление расширения без потери пользовательских workflow и
    карточек.
14. Длинная сессия: рост очереди, кэша и БД.

## 15. Ожидаемый результат

Обычный пользователь подключает ComfyUI, устанавливает совместимые
модели и указывает LoRA непосредственно в карточках персонажей.
Narrative Engine автоматически определяет нужные визуальные изменения,
выбирает проверенные workflow, подключает поддерживаемые маски и
контроли, использует кэш и при необходимости предлагает понятные
варианты. Продвинутый пользователь может подключать дополнительные LoRA
и регистрировать собственные workflow через адаптеры.

**Главный критерий качества:** для игры в визуальную RPG пользователю не
нужно изучать внутреннее устройство ComfyUI.

## Дополнение: адаптация промптов, коррекция артефактов и компоновка сцены

### 1. Цель дополнения

Расширить автоматизированную визуализацию Narrative Engine так, чтобы система учитывала особенности конкретного чекпоинта, формировала подходящие позитивные и негативные промпты, могла корректировать дефекты генерации и поддерживала как отдельную генерацию фона и спрайтов, так и их компоновку в готовую сцену.

Игрок по умолчанию не должен вручную выбирать синтаксис промпта, писать списки тегов, настраивать маски или собирать ComfyUI workflow. Эти операции выполняются расширением автоматически. При этом пользователь должен иметь возможность проверить и при необходимости переопределить настройки в отдельной вкладке «Визуализация».

### 2. Профили промптов чекпоинтов (Checkpoint Prompt Profiles)

#### 2.1. Требование

Для каждого используемого чекпоинта система должна поддерживать профиль, описывающий, как преобразовывать внутреннее описание сцены в промпт, подходящий конкретной модели.

Нельзя считать, что все чекпоинты одинаково понимают теги, естественный язык, порядок описания, веса и негативные промпты. Профиль должен описывать известные возможности и ограничения модели, а не полагаться только на имя файла.

#### 2.2. Поля профиля

Профиль должен по возможности содержать:

- стабильный идентификатор и отображаемое имя модели;
- семейство/архитектуру модели и доступные метаданные;
- предпочитаемый формат промпта: теги, естественный язык или смешанный формат;
- правила порядка и группировки частей промпта;
- поддерживаемый синтаксис весов и специальных конструкций;
- поддержку негативного промпта и особенности его использования;
- рекомендации по качеству, стилю, разрешению и соотношению сторон;
- совместимость с VAE, LoRA, ControlNet, IP-Adapter и другими компонентами, если это применимо;
- поддерживаемые типы задач: фон, персонажный спрайт, компоновка, inpainting, цельная сюжетная иллюстрация;
- происхождение настроек: встроенный профиль, метаданные, пользовательская настройка или экспериментально подобранные параметры;
- уровень уверенности и дату/версию проверки профиля.

Поля, которые невозможно достоверно определить автоматически, должны оставаться неизвестными или требовать проверки. Система не должна выдавать предположение за подтверждённую совместимость.

#### 2.3. Определение профиля

При подключении ComfyUI и обнаружении чекпоинта система должна:

1. Получить доступные сведения о модели и её метаданных.
2. Найти встроенный профиль для известной модели.
3. Если профиль отсутствует, предложить безопасные настройки по умолчанию и возможность выбрать формат вручную.
4. При необходимости запустить тестовую генерацию на небольшом наборе проверок.
5. Сохранять профиль и пользовательские переопределения между перезапусками.

Тестовая генерация может помочь подобрать формат, но не должна считаться абсолютной гарантией качества. Переопределения пользователя должны иметь приоритет над автоматически подобранными значениями.

### 3. Единый формат визуального задания и Prompt Compiler

#### 3.1. Разделение смысла сцены и синтаксиса модели

LLM-режиссёр должен описывать желаемый результат в структурированном внутреннем формате, а не самостоятельно конструировать окончательную строку промпта для конкретного чекпоинта.

Внутреннее визуальное задание (Visual Intent) должно по необходимости включать:

- тип операции и тип результата;
- локацию, время суток, погоду, фон и освещение;
- идентификаторы персонажей;
- внешность, отличительные черты, текущую одежду и аксессуары;
- эмоции, позы, действия и направление взгляда;
- взаимное расположение персонажей и предметов;
- ракурс, крупность плана, кадрирование и композиционные ограничения;
- требуемый стиль;
- обязательные визуальные признаки;
- запрещённые или нежелательные признаки;
- дефекты предыдущего результата, если выполняется коррекция;
- требования к альфа-каналу, маскам, слоям и выходному формату;
- ссылки на ресурсы мира: профиль персонажа, фон, спрайт, предметы, референсы и LoRA.

Не все поля обязательны для каждой задачи. Для отсутствующих данных должны использоваться явные значения «не задано» или безопасные правила по умолчанию, а не выдуманные сведения.

#### 3.2. Сборка промпта

Prompt Compiler преобразует Visual Intent в фактические позитивный и негативный промпты с учётом:

1. текущего состояния мира;
2. карточек и визуальных профилей персонажей;
3. текущей одежды, эмоций, поз, действий и предметов;
4. выбранного типа изображения и ракурса;
5. профиля стиля;
6. профиля чекпоинта;
7. выбранного workflow и его технических ограничений;
8. активных правил коррекции артефактов.

Компилятор должен удалять дубликаты, обнаруживать противоречия, контролировать длину и не добавлять нерелевантные сведения. Например, описание обуви не обязательно для крупного плана лица, но может быть необходимо для спрайта в полный рост.

При конфликте приоритетов компилятор должен применять определённую политику. В общем случае актуальное состояние мира и явные ограничения текущей сцены важнее устаревших описаний из истории. Неизменяемые признаки идентичности персонажа должны сохраняться, если пользователь или сюжет явно не задаёт изменение.

Система должна сохранять для диагностики итоговый промпт, негативный промпт, профиль чекпоинта, использованные источники данных и параметры workflow. Чувствительные данные, не нужные для генерации, в промпт включаться не должны.

### 4. Позитивные и негативные указания

#### 4.1. Позитивный промпт

Позитивный промпт должен формироваться из актуальных и релевантных для текущего изображения данных:

- содержимое и композиция сцены;
- визуальная идентичность персонажей;
- текущая одежда, аксессуары, эмоции и позы;
- расположение предметов и взаимодействие с окружением;
- камера, ракурс, освещение и стиль;
- необходимые для данного чекпоинта теги качества или форматные маркеры.

Система не должна механически добавлять в каждый промпт все известные характеристики мира. Выбор признаков зависит от типа изображения, размера кадра и задачи.

#### 4.2. Негативный промпт

Негативные указания должны формироваться из трёх логических источников:

1. **Базовые указания чекпоинта** — проверенные для выбранной модели и типа задачи.
2. **Контекстные ограничения** — признаки, противоречащие текущей сцене, например лишний персонаж, неверная одежда, дублированный предмет или нежелательная композиция.
3. **Указания коррекции** — признаки, связанные с конкретными дефектами предыдущего изображения.

Негативный промпт должен учитывать возможности модели. Если модель не использует негативный промпт либо использует его иначе, система должна применять подходящий поддерживаемый механизм вместо слепого добавления тегов.

Запрещается бесконтрольно накапливать длинные списки негативных тегов. Необходимо проверять дублирование, конфликты с позитивным промптом и потенциальное подавление нужных деталей. Для разных чекпоинтов и типов задач допускаются разные наборы.

#### 4.3. Проверка противоречий

Перед запуском генерации система должна по возможности обнаруживать противоречия, например:

- позитивный промпт требует очки, а негативный запрещает очки;
- описание требует полный рост, но workflow настроен на крупный портрет;
- текущая одежда персонажа расходится с устаревшим описанием;
- требуется прозрачный фон, но workflow выдаёт только обычное RGB-изображение.

Критические конфликты должны быть разрешены автоматически по правилам приоритетов либо приводить к понятной диагностике до запуска задания.

### 5. Система обнаружения и коррекции артефактов

#### 5.1. Каталог дефектов

Система должна поддерживать расширяемый каталог типовых дефектов, включая, но не ограничиваясь:

- несовпадение идентичности персонажа;
- неверная одежда или аксессуары;
- анатомические дефекты;
- лишние или отсутствующие конечности;
- дефекты кистей и пальцев;
- дублирование персонажей или предметов;
- неверное взаимное расположение объектов;
- ошибки кадрирования и композиции;
- нарушение прозрачности или остатки фона вокруг спрайта;
- несоответствие освещения и масштаба персонажей фону;
- артефакты перекрытия между персонажами и объектами.

Для каждого типа дефекта должны задаваться возможные способы обработки, ограничения применимости и критерии завершения.

#### 5.2. Обнаружение дефектов

Проверка должна использовать доступные инструменты: проверку размеров и альфа-канала, маски, анализ изображений, модели зрения или специализированные детекторы. Обычная текстовая LLM не должна считаться источником достоверной оценки изображения, если ей не переданы изображение или результаты его анализа.

Для каждого результата должна быть возможность получить статус проверки: пройдена, найдены дефекты, проверка недоступна или результат неопределённый. Отсутствие анализатора не должно ошибочно отображаться как подтверждение качества.

#### 5.3. Стратегия коррекции

В зависимости от дефекта система может:

1. повторить генерацию с уточнённым промптом;
2. скорректировать позитивные или негативные указания;
3. выполнить локальный inpainting по маске;
4. пересоздать отдельный спрайт или предмет;
5. пересобрать композицию из сохранённых слоёв;
6. запросить выбор пользователя, если автоматическая коррекция не даёт надёжного результата.

Негативные теги не являются универсальным средством исправления. Например, геометрический дефект руки может потребовать локального inpainting, а неправильное положение персонажа — повторной компоновки или генерации.

Необходимо ограничить количество автоматических повторов, вести журнал попыток и расходов, предотвращать бесконечные циклы и сохранять лучший прошедший проверку результат. При исчерпании лимита система должна показать последнюю доступную версию и понятную причину неудачи.

### 6. Типы визуальных операций и workflow

Workflow Registry должен явно различать следующие типы задач.

#### 6.1. Background Only — отдельный фон

Генерация или обновление фона без персонажей. Результат сохраняется как самостоятельный ресурс локации.

По возможности необходимо поддерживать:
- идентификатор локации и версию фона;
- сохранение стиля, перспективы и основных объектов;
- повторное использование фона между сценами;
- локальное изменение освещения, погоды или выбранных объектов;
- хранение дополнительных масок, глубины или слоёв, если их удалось получить.

#### 6.2. Character Sprite — отдельный спрайт

Генерация персонажа отдельно от фона с требуемой позой, эмоцией и одеждой.

Требования:
- настоящий альфа-канал, когда он нужен;
- проверка прозрачности и границ силуэта;
- применение LoRA персонажа из карточки/визуального профиля согласно основному ТЗ;
- возможность повторного использования и кэширования;
- контроль соответствия внешности и текущего состояния персонажа.

Если выбранная модель не умеет надёжно выдавать альфа-канал, workflow должен использовать совместимый способ отделения фона либо сообщить об ограничении. Нарисованная шахматная подложка не считается прозрачностью.

#### 6.3. Composite Scene — компоновка из слоёв

Сборка сцены из ранее созданного фона, спрайтов и объектов.

Компоновщик должен поддерживать:
- координаты и масштаб персонажей;
- порядок слоёв и правила перекрытия;
- положение относительно мебели и других объектов;
- контактные и падающие тени, если они доступны;
- цветокоррекцию и согласование освещения;
- сохранение масок и вспомогательных слоёв;
- воспроизводимость композиции при повторной сборке.

Для сцен с передними объектами необходимо предусмотреть возможность разделения фона на задний слой и передние элементы. Например, персонаж может находиться позади столешницы, но перед задней стеной. Простого наложения спрайта поверх единого фонового изображения в таких случаях недостаточно.

#### 6.4. Integrated Scene — цельная иллюстрация

Генерация одного изображения, в котором персонажи и окружение создаются совместно. Этот режим используется для сложных взаимодействий, пересечения силуэтов, сюжетных иллюстраций и случаев, когда компоновка из слоёв выглядит неестественно.

Результат должен проходить проверки идентичности персонажей, одежды, композиции и согласованности со сценой. Если необходима дальнейшая анимация или независимое перемещение персонажей, предпочтительно сохранять также отдельные слои/маски, когда workflow способен их предоставить.

#### 6.5. Inpainting / Local Repair — локальная коррекция

Локальное изменение заданной области изображения с помощью маски. Должны быть определены:
- область изменения;
- контекст, который необходимо сохранить;
- защита неизменяемых областей;
- совместимость с чекпоинтом и workflow;
- критерии проверки результата.

Система не должна предполагать, что inpainting всегда сохраняет идентичность и все детали вне маски без изменений. После коррекции необходима проверка результата.

### 7. Компоновка персонажей и фона

#### 7.1. Состояние композиции

Для каждой сцены необходимо хранить или восстанавливать согласованное описание композиции:
- используемый фон и его версия;
- расположение персонажей и объектов;
- масштабы и точки опоры;
- порядок слоёв;
- необходимые маски и области перекрытия;
- текущий ракурс и кадрирование;
- источники спрайтов и их визуальные версии.

Это состояние должно быть связано с моделью мира и не заменяться исключительно описанием в текстовой истории.

#### 7.2. Согласованность фона и персонажей

Workflow компоновки должен по возможности учитывать:
- соответствие масштаба персонажа мебели и архитектуре;
- точки контакта ног с полом или тела с поверхностью;
- направление и мягкость теней;
- цветовую температуру и направление освещения;
- перспективу;
- перекрытие столами, креслами и другими предметами;
- согласованность стиля.

Если для достоверной компоновки недостаёт данных, система должна выбрать более надёжный workflow или выполнить интегрированную генерацию, а не выдавать заведомо ненадёжное наложение за корректную сцену.

#### 7.3. Изменение камеры

Необходимо различать:
- **кадрирование** — изменение масштаба, обрезки и положения кадра в пределах имеющегося изображения;
- **новый ракурс** — получение перспективы, которая не содержится в исходном изображении.

Кадрирование по возможности должно обходиться без повторной генерации. Для нового ракурса могут потребоваться дополнительные референсы, отдельные слои, карты глубины или повторная генерация. Система не должна обещать достоверное восстановление невидимых областей сцены из одного 2D-фона.

### 8. Правила выбора workflow

Выбор workflow должен осуществляться по типу задачи, доступным возможностям моделей и требованиям к результату, а не только по названию чекпоинта.

Примеры правил:
- диалоговая сцена с независимыми спрайтами и неизменным фоном — `Composite Scene`;
- новая локация без персонажей — `Background Only`;
- изменение эмоции персонажа при сохранении фона — обновление спрайта и повторная компоновка;
- сложное физическое взаимодействие нескольких персонажей — `Integrated Scene` либо комбинированный workflow;
- исправление дефекта кисти — локальный `Inpainting / Local Repair`, если подходящий workflow доступен;
- изменение только кадрирования — операция камеры без полной перегенерации.

Capability Resolver должен проверять наличие совместимого чекпоинта, необходимых моделей, LoRA, узлов и входов/выходов workflow. Если требуемая операция недоступна, расширение должно предложить ближайший поддерживаемый вариант или объяснить ограничение.

### 9. Настройки интерфейса

В отдельной вкладке «Визуализация» необходимо предусмотреть разделы:

- **Чекпоинты и профили промптов:** просмотр активного профиля, выбор формата, проверка совместимости, пользовательские переопределения.
- **Промпты:** просмотр итоговых positive/negative prompt, режим диагностики, настройки базовых тегов.
- **Коррекция качества:** включение проверки, лимит повторов, доступные способы коррекции и журнал дефектов.
- **Типы генерации:** фон, спрайт, компоновка, цельная иллюстрация, локальная коррекция.
- **Слои и композиция:** правила размещения, порядок слоёв, тени, маски и параметры кадрирования.
- **Диагностика:** используемый чекпоинт, профиль, workflow, применённые LoRA, время и статус задания, причина отказа или коррекции.

Основной режим остаётся автоматическим. Технические детали доступны для диагностики и экспертного режима, но не должны требоваться для обычной игры.

### 10. Кэширование и версии ресурсов

Кэш должен учитывать не только персонажа и чекпоинт, но и параметры, влияющие на результат:
- идентификатор/версию Visual Intent;
- версию профиля чекпоинта и компилятора промптов;
- позитивный и негативный промпты;
- модель, VAE, LoRA и их веса;
- тип workflow и его версию;
- исходный фон, спрайты, маски и референсы;
- параметры генерации и коррекции.

Изменение значимого параметра должно приводить к корректному обновлению ключа кэша. Система не должна повторно использовать результат, созданный с несовместимым профилем или устаревшей версией исходного ресурса.

### 11. Дополнительные критерии приёмки

1. Один и тот же Visual Intent можно преобразовать в формат тегов и в формат естественного языка без изменения смысла сцены.
2. При смене чекпоинта применяется соответствующий профиль, а логика мира и режиссёра не переписывается.
3. Система не выдаёт неподтверждённую совместимость модели или LoRA за гарантированную.
4. Позитивные и негативные указания формируются из актуального состояния сцены и проходят проверку очевидных конфликтов.
5. Нерелевантные признаки не добавляются в промпт автоматически без необходимости.
6. При обнаружении дефекта система выбирает допустимый способ коррекции, ограничивает число попыток и сохраняет лучший результат.
7. Система различает генерацию фона, спрайта, компоновку, интегрированную иллюстрацию и локальную коррекцию.
8. Прозрачность спрайта проверяется по альфа-каналу, если workflow заявляет поддержку прозрачного результата.
9. Компоновка поддерживает порядок слоёв и случаи, когда объект переднего плана должен перекрывать персонажа.
10. Смена кадрирования не вызывает полную генерацию без необходимости; новый ракурс не считается эквивалентным простому кадрированию.
11. Если подходящего workflow или анализатора нет, пользователь получает понятное сообщение, а система не утверждает, что задача выполнена успешно.
12. Диагностика позволяет определить, какой Visual Intent, профиль, промпты, LoRA и workflow использовались для конкретного результата.

### 12. Дополнительные тестовые сценарии

- Из одного Visual Intent формируются корректные промпты для двух чекпоинтов с разными предпочтительными форматами.
- При неизвестном чекпоинте используется безопасный резервный профиль и показывается степень неопределённости.
- Противоречащие друг другу позитивный и негативный теги обнаруживаются до запуска либо устраняются по установленным правилам.
- При смене одежды персонажа устаревший спрайт не используется без проверки актуальности.
- Фон генерируется и сохраняется независимо от персонажей.
- Персонаж с прозрачным фоном накладывается на фон с правильным масштабом и порядком слоёв.
- Передний объект, например стол, перекрывает нижнюю часть персонажа согласно описанию композиции.
- При дефекте кисти выбирается доступный способ коррекции, а число повторов ограничено.
- При ошибке альфа-канала результат не принимается как готовый прозрачный спрайт.
- Сложное взаимодействие направляется в интегрированный workflow, если простая компоновка слоёв не способна его корректно представить.
- Запрос на кадрирование не приводит к ненужной полной перегенерации.
- Все параметры и версии, необходимые для воспроизведения результата, фиксируются в диагностическом журнале.

### 13. Указания по реализации

Перед добавлением новых модулей необходимо провести аудит существующего репозитория и отметить для каждой функции: реализовано, реализовано частично, отсутствует. Следует переиспользовать существующие профили, очередь заданий, хранилище ресурсов и механизмы ComfyUI, если они уже покрывают нужные требования.

Необходимо избегать создания дублирующих систем хранения промптов, профилей, workflow и состояний сцены. Новые сущности должны интегрироваться с текущими идентификаторами персонажей и ресурсов, а миграции — сохранять обратную совместимость.

Реализацию рекомендуется вести поэтапно:
1. аудит текущего кода и схема соответствия требованиям;
2. внутренний Visual Intent и профили чекпоинтов;
3. Prompt Compiler и проверка конфликтов;
4. реестр типов workflow и capability checks;
5. компоновка фона и спрайтов;
6. диагностика артефактов и ограниченная коррекция;
7. тесты, документация и проверка на реальных совместимых моделях.

Каждый этап должен иметь автоматические тесты. Успешное прохождение unit-тестов не заменяет проверку реальной генерации через ComfyUI с конкретными моделями.
